Describe an API. Get a working MCP server.

MCP Everything turns a GitHub repository, a documentation site, a service name or a plain-English description into a Model Context Protocol server — then builds it, runs it in a Docker sandbox and calls its tools for real before handing it to you.

Four ways to start

You do not need a machine-readable specification. The research step works from whatever you have.

A GitHub repository

Paste a repository URL. The source, README, code examples and test patterns are read with the GitHub API to work out what the tools should be.

A documentation site

Point at a docs or developer portal URL. The pages are fetched and reduced to text before planning begins.

Just the service name

“Stripe API” is enough. The name is classified and researched from public sources.

A plain-English description

Describe the tools you want in a sentence or two and let the planning step turn that into a concrete tool set.

How a generation runs

One explicit pipeline, not a black box. Every step records its own timings and token usage.

  1. Research

    Your input is classified, then researched from the matching source — the GitHub API for repositories, the live pages for documentation URLs, public sources for a bare service name.

  2. Plan the tools

    The research findings are turned into a concrete list of MCP tools, each with a name, a description and a typed input schema.

  3. Ask, if something is missing

    When there is a genuine gap — which authentication scheme, which endpoints matter — the run pauses and asks. Your answer resumes it without repeating the research.

  4. Build, run, repair

    The server is compiled and started inside a Docker container, then driven over JSON-RPC: initialise, list tools, call them. Failures feed back into up to five automatic repair rounds.

  5. Take the code

    You get the source, package.json, TypeScript config, tests, a Dockerfile and documentation — pushed to a new GitHub repository or a public Gist, or downloaded.

What you actually get

Servers that have been run, not just written

Generation refuses to execute model-written code on the host. Every candidate is built and started in a Docker container, and its tools are invoked over real JSON-RPC before the run is allowed to succeed.

Both MCP transports

Generated servers run over stdio by default — ready for Claude Desktop and other local clients — and over MCP Streamable HTTP when MCP_TRANSPORT=http is set. Built against the MCP TypeScript SDK, pinned to a known version.

The code is yours

Output goes to a repository in your own GitHub account or to a Gist, along with a Dockerfile and a devcontainer definition. Nothing is locked to this platform.

Sign in how you like

GitHub, Google, or an email address and password, with password reset. Conversations and generated servers are scoped to your account.

Resumable conversations

Pipeline state is persisted per conversation, so a run that paused for a clarification picks up where it left off instead of starting over.

A public catalogue

Published servers are browsable and searchable without an account, so you can look before you sign up.

What works today, and what doesn’t

This project is in active development and would rather tell you than let you find out.

Working now

  • Generation from a repository, docs site, service name or description
  • Docker-sandboxed build, run and tool execution, with automatic repair
  • Generated servers speaking stdio and MCP Streamable HTTP
  • Publishing to your own GitHub repository or a Gist
  • GitHub, Google and email sign-in, with password reset
  • The MCP endpoint and its six tools, when the backend is reachable
  • A public, account-free catalogue

Not available yet

  • Hosting servers on our infrastructure. The Kubernetes path has never been run against a real cluster and is not offered.
  • Paid plans and billing. Nothing is for sale. There is no checkout to complete and no price to quote.
  • Authentication for hosted servers. Not implemented, because hosting is not offered.
  • A public MCP endpoint on this domain. The server exists and works; the public route to it is not configured yet.
  • OpenAPI or GraphQL specification input. Despite what you may read elsewhere, no specification parser exists. Use a repository or docs URL instead.

Questions

What is an MCP server?

A Model Context Protocol server exposes tools an AI assistant can call — reading a file, querying an API, searching a database. MCP is the protocol clients such as Claude Desktop use to talk to those tools.

Does it cost anything?

No. Accounts are free and include five generations per month. There is no paid plan available to buy, and no card is collected.

Do you host the server for me?

Not yet. You get the source code, a Dockerfile and a devcontainer definition, pushed to your own GitHub repository or a Gist, and you run it wherever you like. Hosting on our infrastructure is not offered today.

How do I know the generated server actually works?

Because it was run. Each candidate is built and started inside a Docker container and driven over JSON-RPC — initialise, list tools, call them. If that fails the code goes back for repair, up to five times, before the run gives up.

Can an AI agent use this without a human?

Yes. MCP Everything exposes its own MCP server over Streamable HTTP with six tools, authenticated with an API key. Create a key on your account page and send it as X-API-Key or a bearer token.

Can I generate from my OpenAPI specification?

No. There is no OpenAPI or GraphQL parser. Point at the repository or the documentation site instead — that is what the research step is built for.
